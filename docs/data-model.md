# Data model

> Decisions only. The migrations in `backend/migration/` are the source of truth once they exist: a change to one changes this file in the same change.

## Stores

| Store | What lives in it | Why this store | Source of truth or derived |
|---|---|---|---|
| SQLite file at `DATABASE_PATH` | Services, their state, notification targets, the public view setting | Survives a restart and an upgrade on the volume (NFR-1) | Source of truth. Backup is the installer's job (requirements section 7); on Fly.io, volume snapshots |
| Process memory (`memstore/`, `worker/`) | Sessions, CSRF tokens, failed sign-in counts, lockouts, rate-limit counters; schedules, attempts in progress, alerts waiting for delivery or a retry | Must end at a restart (FR-114), or is rebuilt at start (FR-111) | Not rebuilt, except schedules, which are rebuilt from the saved services |
| Deployment configuration (environment) | Admin credentials, every limit, SMTP settings | Set by the installer (FR-57, FR-101) | Source of truth, outside the app. Read once at start |

## Conventions

- IDs: UUIDv7 as 36-character text, generated by the app.
- Timestamps: `DATETIME`, always UTC. Booleans: `INTEGER` 0 or 1. Tables are plural, columns `snake_case`.
- Lists inside a row are JSON text in the order the admin gave them. They are read and replaced whole; no query looks inside them.
- Ownership: single owner, no column.
- Deletion: hard, everywhere. Children go with their parent through `ON DELETE CASCADE`.
- Connection: `foreign_keys` on, WAL journal, a busy timeout of 5 seconds, and write transactions that take the write lock when they begin (`BEGIN IMMEDIATE`). SQLite allows one writer at a time, so write transactions run one after another.
- Retention and volume: only the current state is kept. At most `MAX_SERVICES` services (50) and `MAX_TARGETS_PER_SERVICE` targets each (5). The busiest write is one state update per finished check: about 100 a minute at the limits.

## Relational entities

### Service (table `services`)

Serves: FR-6 to FR-9, FR-20, FR-27, FR-33 to FR-38, FR-41, FR-44 to FR-47, FR-50, FR-51, FR-53, FR-57, FR-59, FR-60, FR-64, FR-65, FR-68, FR-69, FR-75, FR-78. Contract schemas: `ServiceInput`, `Service` (without `state`, `target_count`, `alert_delivery_failed`), `CheckConfig`, `HttpCheck`, `TcpCheck`, `QueryParam`, `HttpHeader`, `HttpBody`, `JsonRule`, `CertificateCheck`, `CheckSettings`.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | TEXT | no | |
| `name` | TEXT | no | As the admin typed it |
| `name_key` | TEXT | no | `name` in lower case by Unicode rules, written by the app with every write of `name` |
| `check_type` | TEXT | no | `http` or `tcp` |
| `http_method` | TEXT | yes | Set for `http`, null for `tcp` |
| `http_url` | TEXT | yes | Set for `http`, null for `tcp` |
| `http_query_params` | TEXT | no | JSON list of `{"name","value"}`. Default `[]` |
| `http_headers` | TEXT | no | JSON list of `{"name","value"}`. Default `[]` |
| `http_body_type` | TEXT | no | `none`, `json`, `text` or `form`. Default `none` |
| `http_body_content` | TEXT | no | Default empty |
| `json_rules` | TEXT | no | JSON list of `{"field","failing_value"}`; the value is a JSON string or boolean. Default `[]` |
| `json_rule_mode` | TEXT | no | `any` or `all`. Default `any` |
| `cert_check_enabled` | INTEGER | no | Default 0 |
| `cert_min_days_left` | INTEGER | yes | Set when the certificate check is on |
| `ignore_cert_errors` | INTEGER | no | Default 0 |
| `tcp_host` | TEXT | yes | Set for `tcp`, null for `http` |
| `tcp_port` | INTEGER | yes | Set for `tcp`, null for `http` |
| `check_interval_seconds` | INTEGER | no | The value in force: the configured default is written when the admin gave none |
| `timeout_seconds` | INTEGER | no | As above |
| `retry_count` | INTEGER | no | As above |
| `retry_interval_seconds` | INTEGER | no | As above |
| `alerts_enabled` | INTEGER | no | Default 1 |
| `unhealthy_message` | TEXT | no | Surrounding spaces removed before saving. Left out, null or empty in the request is stored as empty, which means the default message |
| `recovery_message` | TEXT | no | As above |
| `shown_on_public_view` | INTEGER | no | Default 0 |
| `paused` | INTEGER | no | Default 0 |
| `created_at`, `updated_at` | DATETIME | no | |

- Primary key: `id`.
- Unique: `name_key` (FR-59, names unique ignoring case).
- Indexes: the unique index on `name_key` also serves the ordering of `listServices` and `getPublicDashboard` (`ORDER BY name_key, id`).
- Constraints in the database: `check_type`, `http_body_type` and `json_rule_mode` are limited to their values; an `http` row has a method and URL and no TCP columns, a `tcp` row has a host and port and no method or URL.
- Rules enforced in code instead: every length, count and range limit, because the limits are configuration. A saved value is used as it is; it is validated only when it is saved, so a later change of a limit does not touch saved services.
- The default message is applied when an alert is built. It is never copied into the row.
- A change of type (FR-66) writes the new type's columns and resets the other type's columns to null or their defaults in the same update.

### Service state (table `service_states`)

Serves: FR-54, FR-55, FR-61, FR-62, FR-66, FR-78, FR-111, FR-112, NFR-1. Contract schemas: `ServiceState`, `FailureReason`.

| Column | Type | Null | Notes |
|---|---|---|---|
| `service_id` | TEXT | no | |
| `status` | TEXT | no | `not_yet_checked`, `healthy` or `unhealthy`. Default `not_yet_checked` |
| `last_checked_at` | DATETIME | yes | When the last check, retries included, finished |
| `last_status_change_at` | DATETIME | yes | Set whenever `status` takes a new value, the first result included |
| `failure_code` | TEXT | yes | One of the seven `FailureReason.code` values. Null unless `status` is `unhealthy` |
| `failure_http_status` | INTEGER | yes | For `non_2xx_status` |
| `failure_json_rule_field` | TEXT | yes | For `json_rule_matched` |

- Primary key: `service_id`.
- Foreign keys: `service_id` → `services.id`, on delete cascade (FR-70).
- Constraints in the database: `status` and `failure_code` are limited to their values; `failure_code` is null unless `status` is `unhealthy`.
- The row is inserted in the same transaction as its service and exists for as long as the service does.
- Only the check-result usecase writes this table. Add, edit, pause and resume never update it (FR-66, FR-78).

### Notification target (table `targets`)

Serves: FR-14 to FR-19, FR-80, FR-81, FR-86, FR-87, FR-88, FR-92, FR-110. Contract schemas: `TargetInput`, `EmailTargetInput`, `WebhookTargetInput`, `Target`, `HttpHeader`.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | TEXT | no | |
| `service_id` | TEXT | no | |
| `name` | TEXT | no | Empty when none was given |
| `type` | TEXT | no | `email` or `webhook` |
| `value` | TEXT | no | The email address or the webhook URL, with surrounding spaces removed |
| `value_key` | TEXT | no | For `email`, `value` in lower case; for `webhook`, the same as `value`. Written by the app with every write of `value` |
| `headers` | TEXT | no | JSON list of `{"name","value"}`; `[]` for `email`. Default `[]` |
| `last_delivery_failed` | INTEGER | no | Default 0 |
| `created_at`, `updated_at` | DATETIME | no | |

- Primary key: `id`.
- Unique: (`service_id`, `type`, `value_key`) (FR-88: no duplicate contact in one list; email ignores case, a URL is compared exactly).
- Foreign keys: `service_id` → `services.id`, on delete cascade (FR-70).
- Indexes: the unique index starts with `service_id` and serves `listTargets`, ordered by `created_at, id`.
- Constraints in the database: `type` is limited to its values.
- Only the delivery-outcome usecase writes `last_delivery_failed`. Editing a target, its contact included, keeps the value.

### Settings (table `app_settings`)

Serves: FR-26. Contract schema: `PublicViewSettings`.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | INTEGER | no | Always 1 |
| `public_view_enabled` | INTEGER | no | Default 0 |
| `updated_at` | DATETIME | no | |

- Primary key: `id`, with a check that it is 1. The migration inserts the one row; the app only updates it.

`schema_migrations` belongs to golang-migrate and is not touched by the app.

## Rules across entities and stores

- **Service cap (FR-60):** the count and the insert run in one write transaction. Write transactions run one at a time, so two concurrent adds at the limit leave exactly the limit.
- **Target cap (FR-19):** the same, counting the service's targets.
- **Name and contact uniqueness (FR-59, FR-88):** the unique indexes. The repository turns the constraint error into the domain's sentinel error; no check-then-insert.
- **A service and its state row** are inserted in one transaction.
- **`Service.target_count` and `Service.alert_delivery_failed`** are computed in the `listServices` and `getService` queries from `targets`. They are not stored.
- **`PublicService`** is read from `services` and `service_states`: public view on, `shown_on_public_view`, not paused, status `healthy` or `unhealthy` (FR-113).
- **A result for a service that was deleted meanwhile** (a check result or a delivery outcome) updates no row and is dropped. An update never re-creates a row.
- **Status change, then alerts:** the state update commits before the alerts are handed to the delivery loop in memory. If the app stops in between, those alerts are not sent and are not recovered (FR-111).
- **Database, then scheduler:** the scheduler is told after the transaction commits. If the app stops in between, the start-up rebuild puts the schedule right.
- **Tests before saving (FR-105, FR-108)** read and write nothing in the database.

## Not stored

Sessions and CSRF tokens; failed sign-in counts and lockouts; rate-limit counters; schedules and next check times; attempt and retry counts; alerts waiting for delivery; check history and past results; test results and response bodies; a delivery log; the admin credentials; the limits; SMTP settings.
