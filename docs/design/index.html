Monitory UI design

Reference design for the self-hosted uptime monitor described in ui-design-brief.md. Five screens, every listed state, at desktop width (1120 px) and 360 px. Built for React + Base UI, plain CSS with custom properties and Lucide icons.

Visual direction: Instrument panel

For one technical admin who wants dense, quick, keyboard-first screens.

  • Graphite on near-white, one accent. Blue is reserved for actions, links, selection and focus, so it never competes with status colours.
  • Dense by default, roomy when small. 13 px text and 30 px controls on desktop; at under 640 px controls grow to 44 px and inputs to 16 px text (no iOS zoom). Hairline rules instead of cards; no decorative shadows.
  • Machine values in monospace. Times, URLs, header values, codes and response bodies use the system monospace face with tabular numbers, so columns of times line up.
  • Status never by colour alone. Each status has its own icon, word and badge shape (solid round, dashed outline, squared neutral). Colours also differ in lightness.
  • Focus always visible. A 2 px accent outline with a 2 px offset on every focusable element (:focus-visible); boards draw it with .is-focus.
  • System fonts, Lucide icons only, inline SVG at 14 or 16 px, stroke 2. Light and dark themes from the same tokens.

Layout switches use a container query on .app, so one set of markup is shown at both widths. In the app, put .app on the root element and the queries behave like viewport media queries. Styles may be copied into the project’s tokens; the board markup is reference, not component code.

Destructive actions and confirmations

ActionConfirmation in this design
Delete a serviceAlertDialog naming the service and its number of notification targets. Focus on Cancel; Esc cancels. (Dashboard › Delete confirmation)
Remove a notification targetProposed: inline two-step confirm in the row (“Remove this target? Cancel / Remove”), no dialog. (Alert list › Remove a target)
Pause a serviceNone. Toast confirms; Resume is the same button.
Turn the public view offNone. The switch’s On/Off label changes at once.
Sign outNone (unless a form has unsaved changes, see below).
Leave a form with unsaved changesProposed: AlertDialog “Discard unsaved changes?” with Keep editing (focused) / Discard changes, on Cancel, back, Sign out or Esc; the browser’s own prompt on tab close or reload. (Service form › Leave with unsaved changes)

Open questions

States that seem to need data or an error the brief’s error table doesn’t list. None of these is built beyond what is noted.

  1. “Last delivery failed” on the dashboard. The brief puts this notice on each dashboard row, but its source, Target.last_delivery_failed, comes only from listTargets (one call per service, not part of listServices). Showing it means up to 50 extra requests on every load and every 5-minute refresh. Is that acceptable, or should the dashboard get this from another source? The design assumes the per-service calls.
  2. Limits in validation errors. errors[] carries field and code only. For out_of_range on the timing fields the design can only say “Outside the range this server allows”, because limits differ per install and aren’t readable. Could the error include the allowed range? And are the length limits in the brief (name 100, messages 500, target name 50) fixed? The design shows counters such as “37/100” for those three; if they can change per install, the counters should go.
  3. “Service limit reached” as a dashboard state. The only source is createService 409, which happens when the form is saved. The dashboard can’t know the limit beforehand, so the design shows the refusal in the form and leaves Add service enabled. Is that what was meant, or is something expected on the dashboard itself?
  4. Not-yet-checked services on the public page. The public page shows only Healthy or Unhealthy. What does getPublicDashboard return for a public service that hasn’t been checked yet (status and last-check time)? Is it left out, or does it need a third look? Nothing is drawn for it.
  5. Values typed before a session expires. On 401 the brief says return to sign-in, which loses whatever was typed in the service or target form. Should the client keep a draft and restore it after signing in? It needs no new API, but it isn’t in the requirements, so it isn’t drawn.
  6. Target count in the delete confirmation. The count comes from listTargets for that service. The design reuses the dashboard’s per-service data (question 1) and fetches it when the dialog opens if it’s missing; Delete waits for the count. Confirm.
  7. Failure reason values. openapi.yaml wasn’t attached to this chat, so the reason wording (dashboard › Failure reason wording) is keyed by description. Map it to the real last_failure_reason values, and confirm where the HTTP status code (non-2xx) and the field path (JSON rule matched) come from.
  8. Public page link and title. The dashboard’s “Open public page” link needs the public page’s path. There is no title setting, so the public page’s heading is the fixed “Service status”. Confirm both.
