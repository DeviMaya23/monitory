# Conventions

> Applies to all implementation agents. Stack and libraries: `STACK.md`. Directory structure: `ARCHITECTURE.md`. Testing: `TESTING.md`. What needs the user's approval: `AGENTS.md` ("Decision Boundaries").

---

## Project rules

These come straight from the requirements. Do not work around them.

1. **`docs/openapi.yaml` is the contract.** Types are generated from it. Do not edit it; ask.
2. **API errors are `application/problem+json` with a `code` from `docs/openapi.yaml`.** Clients branch on `code`, never on message text. Never expose internal error text. Do not add a code the spec lacks; a temporary `not_implemented` for stubs is the only exception.
3. **Every `FieldError` has a `message` that states the limit in force on this install**, built from the configured value, and a `field` path in the contract's syntax (`check.headers[2].value`). The frontend shows `message` as it is.
4. **IDs are UUIDv7 generated by the app. Timestamps are UTC, RFC 3339 in JSON** and in alerts, where the text says "UTC" (FR-93). The frontend shows local time (FR-94).
5. **Every operation not marked public in `docs/openapi.yaml` requires the session**, and gated operations that send data require the CSRF token (FR-4, NFR-8). Both are applied in one place (`ARCHITECTURE.md`). There is no dev or test bypass.
6. **No limit is a literal.** Every value the requirements mark "do not hardcode", and every default, minimum and maximum of FR-57, comes from `platform/config` and is passed in. The fixed limits are named constants in `domain/`: message length 500 (FR-65), target name length 50 (FR-87), session lifetime 30 days (FR-5), 5 failed sign-ins and a 15-minute lockout (FR-2).
7. **Nothing is saved on a rejection** (FR-12). Validate everything, collect every field error, then write once.
8. **Content from the admin and from checked services is plain text end to end** (NFR-7): names, messages, failure reasons, response bodies. The frontend never renders it as HTML (no `dangerouslySetInnerHTML`); email alerts are plain text.
9. **An alert never contains the response body, headers or request settings** (FR-23). **The public dashboard returns name, status and last check time only** (FR-40, FR-63); its response type has no other field to fill.
10. **A test changes no saved state** (FR-105, FR-108): no status, time, failure reason or delivery notice is written, and no alert is sent. Test code paths take no repository that can write.
11. **Outbound connections go through `adaptor/` only**: checks through `adaptor/probe`, email through `adaptor/mailer`, webhooks through `adaptor/webhook`. Private addresses are allowed (requirements section 6). A webhook delivery does not follow redirects (FR-115); a check follows up to the configured number and re-sends the saved headers (FR-58).
12. **Sessions, failed sign-in counts, lockouts and rate-limit counters are never stored** (FR-114). They live in `memstore/`.
13. **Status changes and their alerts are decided in one usecase.** A status change is saved before its alerts are handed to the delivery loop. A delivery failure never changes a service's status (FR-84), and one target's failure never stops another's delivery (FR-83).
14. **Caps and uniqueness hold under concurrent requests**: 50 services (FR-60), 5 targets per service (FR-19), service names unique ignoring case (FR-59), no duplicate contact in one list (FR-88). `docs/data-model.md` says which the database enforces and which the code enforces inside a transaction.
15. **The public view's limit is a fixed window**: the configured number of requests per client address per minute, with `Retry-After` set to the seconds left in the window (FR-32). The client address comes from the policy router (FR-99).
16. **Wrong credentials and a locked account give no hint** about which part was wrong (FR-1). Compare the username and the password in constant time, and always compare both.

## Logging

`log/slog`, one JSON line per event, to stdout.

- Logged: startup configuration with secrets left out; service id and name; check outcome and failure reason; alert delivery outcome per target id; sign-in failures and lockouts; unexpected errors.
- Never logged: passwords, session and CSRF tokens, check URLs, query parameters, headers, request and response bodies, email addresses, webhook URLs.
- Only `cmd/`, `handler/` and `worker/` log. Usecases, repositories and adaptors return errors.

## Git

- Branch names: `feat/<slug>` for a builder, `verify/<slug>` for a verifier. The scripts find a branch by its files, not its name.
- Task pull requests are squash-merged by the user.
- A push that changes only documentation has a commit subject that starts with `docs:`.
- Generated code (`backend/internal/api`, `frontend/src/lib/api/schema.d.ts`) is committed and changes only through `make generate`.

Do not suppress findings: no `eslint-disable`, `//nolint`, `stylelint-disable`, `shellcheck disable` or `markdownlint-disable` comments. Fix the underlying issue. Exception, with a comment explaining why: `react-hooks/exhaustive-deps`.

## Frontend

### Design reference

`docs/design/` is read-only. Copy token values and style rules into `frontend/src/styles/`; never copy board markup. `docs/design/README.md` lists where the boards differ from what is built.

### Components

- Only the wrappers in `components/ui/` import Base UI. Before writing a dialog, switch, select, tabs, tooltip, menu or toast, use the wrapper; if it does not exist, add the wrapper. Never hand-write a replacement for something Base UI provides.
- Icons come from Lucide only.
- Colours, spacing, type sizes and radii come from the tokens. No literal colour or pixel value in a feature stylesheet where a token exists.
- Status is never shown by colour alone: icon, word and badge shape, as in the design.
- Every interactive element is reachable by keyboard and shows the focus outline (NFR-4).

### Forms

Forms use react-hook-form. The client checks only that required fields are filled and that a URL's scheme allows the HTTPS options. Everything else is validated by the server: map each `errors[].field` to its input and show `errors[].message`. A field error clears when that field is edited.

### Component and hook granularity

When building a component, split out a hook for each cohesive concern (state, its effects and its handlers). A concern is cohesive if one sentence describes it without mentioning the rest of the component.

- One hook per concern, with a colocated test file (`useThing.ts` + `useThing.test.ts`), written in the same step as the hook, not afterwards.
- Hooks return semantic mutators (`removeHeader(index)`, `pauseService(id)`), never raw setters.
- Group the DOM handlers a hook exposes into one object meant to be spread (`inputProps`), not many loose handlers.
- If a hook attaches effects to a DOM ref (`ResizeObserver`, native listeners), test it through a small harness component with `render()`, not bare `renderHook`.

### Matching existing shapes

Before writing a new dialog, confirmation or list-row component, check whether the feature or a sibling already has one of the same kind and match its shape. Do not introduce a new generic shared component to save a few lines on the first or second occurrence; that is a new cross-feature abstraction and needs the user's approval. Two near-identical feature-owned components are fine; share once a third appears or the duplication is large.

### No duplicated logic across entry points

Before copy-pasting a flow to wire up a new entry point, check whether it should call into, or be factored alongside, the existing implementation.

- A pipeline used from more than one place is one function in `lib/`, parameterised by what varies. Keep validation separate so each caller's error convention still works.
- Near-identical UI components (the header rows of the service form and of the target form): build the shared generic implementation first, then thin wrappers.
- The bar is duplicated logic with drift risk (a fix would need to land in N places), not file size.

### State management

Server data lives in TanStack Query, never copied into component state. Local state that holds an optimistic or in-flight value (an edit buffer while its request is in flight) may re-sync from props. Local state that is purely derived is the smell: fix it with a `key` remount or `useMemo`.

## Backend

### Errors

Usecases return domain sentinel errors. Handlers map each to its `code` and status in `docs/openapi.yaml`. Anything unmapped becomes a generic 500 with no internal detail.

### Time and concurrency

- All time goes through the clock (`ARCHITECTURE.md`).
- Every goroutine has an owner that can stop it and wait for it. No goroutine is started from a handler or a usecase; background work belongs to `worker/`.
- Every outbound call takes a context with a deadline.
- Tests run with the race detector.

### Go version and dependencies

The `go` directive in `go.mod` is a deliberate choice. Upgrades happen only when the user asks.

`go get` and `go mod tidy` silently raise the `go` line (and add `toolchain`) when a dependency declares a higher version. After any dependency change, check `git diff go.mod`. If `go` or `toolchain` changed:

1. Revert that change.
2. Find an older version of the dependency that works (`go list -m -versions <module>`, then `go get <module>@<version>`).
3. If none exists, stop and tell the user which dependency needs which Go version. Do not bump it yourself.
